## 二、按可能性排序的根因假设（附代码证据）

### 假设 1（最确定）：二面角噪声上界/下界不一致 —— `diffusion.py:46-47` vs `model_parameters.yml:144-145`

- `MultiRateDiffusion.__init__` 硬编码 `tor_sigma_min=0.03, tor_sigma_max=1.55`（注释甚至写着“0.03→1.55”），但真实 DiffDock-L 权重对应的 yml 是 `tor_sigma_max=3.14, tor_sigma_min=0.0314`。
- 后果是**分数与反向步的 σ 不自洽**：
  - 分数侧：`expert.py:205` `edge_sigma = tor_sigma[data['ligand'].batch][tor_bonds[0]]`，其中 `tor_sigma` 来自 `model.t_to_sigma`（`expert_factory.py:68` 用 yml 参数），即 **3.14/0.0314**。
  - 反向侧：`diffusion.py:455-456` `tor_sigma = self.t_to_sigma(...)` 用 **0.03/1.55**。
- t=1 处 `tor_g²` 偏低 (4.35/9.53)² ≈ **0.21×**。这是唯一的“硬编码常量与权重文件不一致”的 bug，方向明确、量级可量化。

### 假设 2（高度确定）：二面角温度采样缺失 —— `diffusion.py:458-461` vs `sampling.py:202-205`

- tr/rot 温度采样在 `reverse_step_protac` L366-398 正确复刻（与 `sampling.py:192-200` 逐项一致），唯独 `reverse_step_torsion` L458-461 回到朴素 Euler-Maruyama，没有 `temp_sampling[2]=7.04` 分支。
- `diffusion.py:51` 已定义 `temp_sampling_tor=7.04`，但**从未被读取**（静默失效）。
- 与假设 1 叠加：t=1 时二面角漂移系数 = `tor_g²·(λ_tor+ts·ψ/2)`，原生 ≈ 9.53²·5.31 = 482，TriCoopDiff ≈ 4.35²·1.0 = 18.9，比值 **~25× 过弱**；而噪声只弱 ~2.8×。→ **二面角信噪比被压低 ~9×，去噪方向被噪声淹没**。

### 假设 3（已修，patch #3；正文的“方向相反”是 BUG-18 修复前的判断，已被 L6 状态行取代）：初始化策略不一致 —— `diffusion.py:616-705` vs `sampling.py:16-58`

- **旧代码（patch #3 前）**：`initialize_protac` 从 PROTAC 模板 COM（`sampler.py` `pocket_center = ligand_template.mean(0)`）外 0–10 Å 球壳出发，且**保留模板二面角**（不随机化）。**BUG-18 修复后**模板 COM 被重表达为 `lig_offset`（≠0，见 `featurize_common.py:_true_relative_offsets`），`pocket_center` 不再是受体 COM → 32 walker 从离口袋 20+ Å 处起步，去噪拉不回 → 0.0925 回归根因。patch #3 已改为原生 `randomize_position`（`sampler.py:88-100` 用 `e3_center = e3_coords.mean(0)`，`initialize_protac` 原生分支随机二面角 + 绕 COM 旋转 + N(0,19²)）。
- 原生 `randomize_position`：二面角均匀随机 [-π,π]，把配体平移到受体 COM（`receptor.pos.mean(0)`），再加 `N(0, tr_sigma_max²)` 高斯平移（`initial_noise_std_proportion=-1.0`，见 `sampling.py:52-57` → std = 19.0）。
- 关键（BUG-18 修复后的重判）：初始分析（BUG-18 前）认为 TriCoopDiff 初始化**比原生更接近答案**（0–10 Å 壳、模板二面角），会让结果**更好而非更差**，故不解释 50 Å 漂移。但 BUG-18 重表达把模板 COM 移到 `lig_offset`（≠0），`pocket_center = ligand_template.mean(0)` 使 walker 起步即错位 20+ Å——方向**由“更好”翻转为“灾难性更差”**，成为 0.0925 回归根因（见 L6 状态行）。patch #3 已修复，待重跑验收。

### 假设 4（次要）：步数/末步时间不一致 —— `diffusion.py:73/557` vs `default_inference_args.yaml:1/8`

- 原生 `actual_steps=19`（末步 t=0.10、dt=0.10），TriCoopDiff `inference_steps=20`（末步 t=0.05、dt=0.05）。
- 纯离散化差异，量级小，不解释 50 Å。

### 假设 5（次要）：受体动态裁剪关闭 —— `expert_factory.py:62-64` vs `sampling.py:108-110`

- `build_diffdock_expert` 强制 `args.crop_beyond = None`（注释理由：POI 子图配体起步远离蛋白、裁剪会删光残基）。代价是 E3-L 子图也失去原生的 `tr_sigma*3+20` 动态裁剪，远距离残基噪声进入分数。
- 影响分数质量（噪声更高）但不会系统性推离 COM 到 50 Å。

### 假设 6（仍需排查）：POI 变换链可能把 sub2 喂进了“对的坐标、错的时刻”

- `model.forward()` 先用 `t_e3_to_poi = poi_center - e3_center` 和 `r_e3_to_poi` 把 PROTAC 转到 POI 帧，再把 POI 分支的 `tr/rot` score 旋回 E3 帧后合并；这条链路本身看起来一致，但它依赖 `poi_data['coords']`、`R_cum` 和 `transform_ligand_to_poi_frame()` 在每一步都严格同步。
- `evaluate.py` 里的 POI / E3-interface 指标是按相对几何计算的，设计上是 frame-invariant，所以更像“采样时的 POI 视角不一致”而不是“评估算错了”。
- 这条线索现在比 score normalization 更值得追：若 POI 侧的 ligand 位置和实际 sampler 状态存在一拍延迟，sub2 的分数就会在错误坐标系上修正 E3-L 轨迹。
- 继续对照后得到的更细结论：`sampler.py` 的 `R_cum` 更新时序与 `poi_pos` **表面上是同步的**——本步 forward 用的是上一步累计的 `R_cum.transpose(-1,-2)`，随后 `reverse_step_se3(..., return_rotation=True)` 返回本步刚施加到 `poi_pos` 的 `rot_matrix`，再做 `R_cum = R_cum @ rot_matrix` 供下一步使用；这与 `reverse_step_se3` 里 `poi_pos = poi_center + (poi_pos-poi_center) @ rot_matrix` 的右乘约定一致。
- 更关键的是，`reverse_step_se3` 的旋转约定和 vendored DiffDock 刚体更新是同一手系：TriCoopDiff 用 `so3_exp(ω)` 后右乘 `@ R`（`diffusion.py:552-553`），native `modify_conformer_batch` 用 `axis_angle_to_matrix(rot_update)` 后右乘 `@ Rᵀ`；而 `so3_exp(ω)` 的 Rodrigues 展开对应的正是 `exp([ω]×)`，与 `axis_angle_to_matrix(ω)` 数值同义。**因此当前没有证据表明 `R_cum = R_cum @ rot_matrix` 本身存在符号/转置 bug。**
- 结论：POI 变换链仍值得动态验证，但静态代码层面暂未找到可直接落 patch 的确定性错误；其优先级低于“缺失 dynamic crop”，高于已基本排除的 score norm / `receptor.node_t` / 评估公式。

## 三、最确定的 1–3 个行级差异（对“分数正确但漂移到 50 Å”的解释力排序）

1. **二面角 σ 不自洽**：`tricoopdiff/diffusion.py:46-47`（硬编码 0.03/1.55）应当等于 `checkpoints/score_model/model_parameters.yml:144-145`（0.0314/3.14）。分数按 σ∈[0.0314,3.14] 归一化，反向步却按 σ∈[0.03,1.55] 积分，`tor_g²` 系统性偏低 ~4.8×。
2. **二面角温度采样缺失**：`tricoopdiff/diffusion.py:458-461` 缺少 `DiffDock/utils/sampling.py:202-205` 的 `temp_sampling[2]=7.04` 分支（而 `diffusion.py:51` 已定义该常数却从未使用）。
3. **初始化不一致**：旧 `tricoopdiff/diffusion.py`（0–10 Å 球壳、不随机二面角、模板 COM 作中心）vs `DiffDock/utils/sampling.py:19/31-39/43-58`（受体 COM + 高斯、随机二面角）。BUG-18 修复后该差异方向翻转，是 0.0925 回归根因；patch #3 已对齐（现 `diffusion.py:616-705`），待重跑。

### 关于“50 Å COM 漂移”的诚实说明

已逐行验证 **tr/rot 反向步与分数归一化与原生等价**（见第四节），因此 50 Å 的 COM（`evaluate.py:718` `np.linalg.norm(pred.mean(0) - ref_lig.mean(0))`）漂移**不是**简单的 tr/rot 符号或尺度 bug 直接造成的。当前最自洽的机制是二阶反馈：二面角反向步信噪比被压低 ~9×（假设 1+2），使 PROTAC 内部构象在 20 步内被随机化（`reverse_step_torsion` L458-461 每步注入 ~1 rad 噪声）；下一轮的 tr 分数是在“形状错误的配体”上计算的，其“最优位置”不再是真实口袋，逐步把 COM 推离。这一链条是否足以解释 49.8 Å 的完整量级，需用第五节的 CPU 脚本数值确认（纯代码阅读无法闭合）。

## 四、已验证一致（非 bug，避免重复排查）

- **tr/rot 温度采样等价**：`diffusion.py:366-398` 与 `sampling.py:192-200` 的 `lambda_tr/rot`、噪声系数 `√(dt(1+ψ))` 逐项一致（含 `tsd·log(σmax)+(1-tsd)·log(σmin)` 的 `σ_data` 内插）。
- **刚性变换等价**：`reverse_step_protac` L409-413 的“平移后绕新质心旋转 @ Rᵀ” = `modify_conformer_batch` 的“绕旧质心旋转 @ Rᵀ 后平移”（`diffusion_utils.py:60-69`）。
- **旋转约定等价**：`so3_exp`（Rodrigues，`diffusion.py:734-768`）与 `axis_angle_to_matrix`（`geometry.py:72-86`）同义，且两者均以 `@ Rᵀ`（`= exp(-[ω]×)`）施加；`reverse_step_protac` L405-408 的注释确认已修复转置方向。
- **分数归一化非重复施加**：`so3.score_norm` / `sqrt(torus_score_norm)` 已烘焙进 `compute_scores`（`expert.py:166-171, 207-212`），反向步不再乘。
- **t→σ 公式等价**：`diffusion.py:107-118` 与 `diffusion_utils.py:28-32` 的指数插值一致。
- **二面角 Kabsch 回对齐**：`reverse_step_torsion` L480-481 调用与原生相同的 `rigid_transform_Kabsch_3D_torch_batch`（`tricoopdiff/diffdock/utils/geometry.py:246-276`，`R=Vtᵀ@Uᵀ`, `t=-R@cA+cB`），COM 被回对齐保留 —— 故二面角 bug 不会直接泄漏到 COM，只会破坏内部构象。
- **零-FiLM 基线在采样路径仍透明**：`FiLMHead`（`tribrain.py:702-703`）与 `MergeGateHead`（`tribrain.py:512-513`）均 `nn.init.zeros_`；`t_se3` 只进入 `SE3ScoreHead`（`tribrain.py:659-667`），不进入 FiLM/merge 路径。故采样器里 `s_q = s_q1 + 0·(s_q2-s_q1) = s_q1` 成立，与 GATE1 一致。

## 五、CPU-only 验证脚本（建议，仅描述，不运行）

目标：纯 numpy/torch、**不 import tricoopdiff**，数值确认“二面角漂移系数 ~25× 过弱”这一核心假设。

1. 定义 σ(t)=σmin·(σmax/σmin)^t。
2. 计算两组 `tor_g`：A（原生）= σ(t)·√(2·ln(3.14/0.0314))；B（TriCoopDiff）= σ(t)·√(2·ln(1.55/0.03))，其中 σ(t) 各自用对应的 σmin/σmax。
3. 对 t∈{1.0, 0.5, 0.1} 计算原生漂移因子 `tor_g²·dt·(λ_tor+ts·ψ/2)`（λ_tor 用 `temp_sigma_data_tor=0.6943, ts=7.044, ψ=0.5946`）与 TriCoopDiff 漂移因子 `tor_g²·dt·1.0`。
4. 输出比值 `B/A`：若 t=1 处 ≈ 1/25（≈0.04），则假设 1+2 成立。
5. 反向验证：把 TriCoopDiff 的 `tor_g` 改为用 3.14/0.0314 且套上温度分支后，B/A 应回到 ≈1。

该脚本无需 GPU、无需 tricoopdiff，可直接在登录节点运行；它只能确认“漂移系数偏小”这一事实，无法模拟完整的 20 步反馈闭环（那需要真实分数，只能在 GPU 上做）。

## Round 1 轨迹级 parity probe（2026-08-18，已接到真实 eval 路径，待 GPU 跑数）

### 同轮新增：sampler 端也回到 native crop regime 的守门逻辑（已落地）

在 `model.py` 按 `dynamic_max_cross` 选择是否裁剪之后，又把 `sampler.py` 里的 cutoff 生成也收回到同一语义：

- 只有 frozen expert 真正处于 `dynamic_max_cross=True` 时，`sampler.py` 才会计算 `receptor_crop_cutoff = tr_sigma * 3 + 20`；
- 若 expert 不是 dynamic-cross，`sampler.py` 现在直接传 `None`，不再伪造一个“数值上有 cutoff、语义上却不会启用”的状态；
- 这样 trace / debug 输出里的 `receptor_crop_cutoff` 才和实际 driver 一致，后续排查不会再把非空 cutoff 误读成 native crop 已介入。

这不是新的行为分歧修复，而是把 sampler 的日志/参数流和 `model.forward()` 的实际判定对齐，防止 trace 误判。


沿着 `model.py -> crop_receptor_to_ligand(...) -> vendored CGModel.forward()` 再对了一轮后，又补了一处更接近 native sampling driver 的收口：

- `tricoopdiff/model.py` 现在先读 `self.expert.model.dynamic_max_cross`；
- 只有 frozen expert 真正处于 `dynamic_max_cross=True` 时，才会把 step-level `receptor_crop_cutoff` 传进 `crop_receptor_to_ligand(...)`；
- 若 expert 走的是 static `cross_max_distance` 语义，则 TriCoopDiff 也保留 full receptor graph，让 `CGModel.build_cross_conv_graph()` 自己在 full-receptor 上处理远距离 pose。

这条 patch 的动机是消除一个此前被轻量 crop 引入的 **non-native hybrid path**：如果 expert 已被构造成 static cross-edge 模式，但 sampler 端仍额外按 `tr_sigma*3+20` 缩 receptor 节点集合，那么实际 forward 走到的是“**static cross cutoff + shrinking receptor node set**”。它既不等于 native `sampling.py` 在 `crop_beyond(...)` 打开时的 `dynamic_max_cross` 路径，也不等于 native 在 `args.crop_beyond=None` 时的 full-receptor fallback。

换言之，这轮不是简单“更激进地裁”或“完全不裁”，而是把 **是否做 step-level receptor crop** 重新绑定回 native DiffDock 真正使用的 driver 条件：只有 expert 本身也处于 dynamic-cross regime 时，这层 crop 才有语义上的对照物。

> 这部分是后来补充的静态代码结论：`crop_beyond` 不是“可有可无的小优化”，而是原生 DiffDock 推理路径的一部分；TriCoopDiff 目前没有接上。

### 原生行为

`tricoopdiff/diffdock/sampling.py` 在每个反向步都会：

1. deep copy 当前 complex graph
2. 按当前 ligand / receptor 距离裁 receptor
3. 再 `set_time(...)`
4. 再 `model(...)`

对应裁剪逻辑在 `tricoopdiff/diffdock/utils/crop.py`：

- 以 ligand 到 receptor 的距离筛 residue
- 同步裁 `receptor.pos`
- 同步裁 `receptor.x`
- 同步裁 `receptor.side_chain_vecs`
- 同步重映射 `('receptor','rec_contact','receptor').edge_index`

### TriCoopDiff 现状

`tricoopdiff/sampler.py` 的真实路径是：

- `sample_single()` 初始化 ligand / POI
- 每步直接组装 `lig_d` / `poi_d`
- 直接喂给 `model(...)`
- **没有任何 step-level receptor crop**

也就是说，zero-FiLM 基线当前看到的是“全 receptor 上的 DiffDock-like forward”，不是 native 的“动态裁剪后 forward”。

### 更关键的新发现：receptor edge schema 其实没有漂移（这条嫌疑可降级）

我这轮专门沿着 `rec_contact → extract_receptor() → build_subgraph_*() → CGModel.embedding()` 静态核对了一遍，结论是：**TriCoopDiff 这里并没有把 native receptor 图喂错 edge type**，此前那条怀疑应当降级。

证据链：

1. vendored featurization 的原始 `HeteroData` 的确写入的是
   `complex_graph['receptor', 'rec_contact', 'receptor'].edge_index`（`tricoopdiff/diffdock/datasets/process_mols.py` / `utils/inference_utils.py`）。
2. 但 `torch_geometric.loader.DataLoader` 在 batch 后会把只有一种 relation 的同构边**扁平化到 canonical homogeneous key**；于是 `featurize_common.extract_receptor()` 读取的 `batch_graph['receptor', 'receptor'].edge_index` 不是“另一张边图”，而是 batch 产物里对这唯一 receptor relation 的规范访问方式。
3. 更重要的是，这条路径前后一致：`extract_receptor()` 导出 `edge_index`，`graphs.py` 再写回 `graph['receptor', 'receptor'].edge_index`，而 vendored `CGModel.embedding()` / `build_rec_conv_graph()` / `forward()` 也**全程只读这一 canonical key**（`data['receptor', 'receptor']`）。也就是说，TriCoopDiff 子图 forward 实际消费的 receptor 图语义，与 batch 后 native `CGModel` 期望的是同一套键。
4. `CGModel` 的 receptor embedding 缓存（`rec_node_attr` / `rec_edge_attr` / `edge_sh` / `edge_weight`）也是挂在 `data['receptor', 'receptor']` 上，而不是 `rec_contact`；这进一步说明 vendored model 在运行态就把 receptor graph 视为 canonical homogeneous relation。

因此，**“extract_receptor 拿错 edge type 导致 zero-FiLM baseline 偏离 native”目前没有静态证据支持**。如果真有 receptor-level 差异，更可能来自：

- 缺失 step-level dynamic crop（最优先）；
- crop 之后缓存失效/重算语义；
- sampler driver 级别其余数据路径差异；
- 或更细的初始化 / reverse loop 行为差异。

### 为什么这很重要

- 远场 residue 会持续进入 cross graph
- cross edge 数量、局部几何感受野、分数归一化都可能偏离 native
- 这能解释一部分“分数透明但采样不复现”的现象

### 但也要注意

TriCoopDiff 的 subgraph schema 很轻量，当前 forward 只依赖：

- `receptor.pos`
- `receptor.x`
- `receptor.batch`
- `('receptor','receptor').edge_index`
- ligand 的 `edge_mask` / `mask_rotate`

所以 native 的 `crop_beyond()` **不能直接原封不动搬进来**，因为它还要求 `side_chain_vecs` 和 `rec_contact`。

进一步看 vendored `CGModel` 的运行语义，这里还有一个很关键的 driver-level 约束：**原生 DiffDock 之所以在每步 forward 前先 deep-copy 再 crop，不只是为了“避免原图被改坏”，更是因为 `model.embedding()` 会把 receptor cache 原地挂回 `data` 上**（`rec_node_attr` / `rec_edge_attr` / `edge_sh` / `edge_weight`；见 `tricoopdiff/diffdock/models/cg_model.py`）。一旦 receptor 节点数或 `edge_index` 在 crop 后变化，而我们又复用上一步已经缓存过的 `HeteroData`，这些 cache 的 shape / 索引语义就可能与新图不一致。

好消息是，**TriCoopDiff 当前每一步其实天然满足“fresh graph”这个前提**：`model.forward()` 里每次都会重新调用 `build_subgraph_e3l()` / `build_subgraph_pol()` 新建 `HeteroData`，然后 `_expert_forward_with_film()` 才在这份新图上调用 `model.embedding()`。这意味着：

1. **如果要补 dynamic crop，最佳落点就是 `sampler.py → model.forward()` 之间的 subgraph 构建阶段**，而不是在一个已 forward 过的 `HeteroData` 上原地裁；
2. 轻量 crop 只需要同步裁 `receptor.pos` / `receptor.x` / `receptor.batch` 并重映射 `('receptor','receptor').edge_index`，就能满足当前 TriCoopDiff forward 的最小需求；
3. 由于 subgraph 是每步新建，crop 后不会继承上一轮的 receptor caches，这一点与 native `deep copy → crop → forward` 的核心语义是一致的。

结论是：**crop 应该补在 sampler/子图构建路径里，但需要一个 TriCoopDiff 专用的轻量裁剪实现；从静态代码看，这个实现与当前 fresh-subgraph 设计是兼容的。**

### 继续深挖后的新结论：`args.crop_beyond = None` 只关掉了“预裁 receptor”，并没有让 TriCoopDiff 更像 native inference

这轮又顺着 `expert_factory.py → diffusion_utils.set_time() → CGModel.forward()` 往下核对了一遍，能进一步排除一个容易混淆的方向：`build_diffdock_expert()` 里把 `args.crop_beyond = None`（`tricoopdiff/expert_factory.py`）**并不会关闭 CGModel 里的动态 cross cutoff**，因为两者根本不是同一个机制。

- `args.crop_beyond` 只被 native `sampling.py` 当作 driver 级的“是否在每步 forward 前先执行 `crop_beyond(...)`”开关；
- `CGModel.forward()` 里的 `if self.dynamic_max_cross: cross_cutoff = (tr_sigma * 3 + 20)` 仍然会正常生效（`tricoopdiff/diffdock/models/cg_model.py`）；它控制的是 **cross edge 的距离阈值**，不是 receptor 节点集合本身；
- 换言之，TriCoopDiff 当前不是“既没 crop 也没 dynamic cross cutoff”，而是“**保留了 dynamic cross cutoff，但缺少 native 的 step-level receptor 节点裁剪**”。

这一区别非常重要，因为它把问题进一步收窄成：

1. **cross edge 半径公式本身大概率不是主因**——native 和 TriCoopDiff 都会随 `tr_sigma` 动态调 cross cutoff；
2. 真正缺失的是 **receptor node set / rec-edge set** 随 ligand 漂移而收缩的那一层 driver 语义；
3. 因此当前 zero-FiLM baseline 偏离 native，更像是“全 receptor 上做 native-style cross-edge 构图”，而不是“cross cutoff 常数写错”。

此外，`diffusion_utils.set_time()` 给 native batch 同时写 `ligand.node_t`、`receptor.node_t` 和 `complex_t`，而 TriCoopDiff 的 `_set_time_embeddings()` 只写 `ligand.node_t` 和 `complex_t`。但结合 `CGModel.embedding()` 可见，receptor 时间嵌入实际取的是 `data.complex_t['tr']` 经 `rec_sigma_embedding(...)` 后按 `receptor.batch` broadcast 回去，并**不读取** `receptor.node_t`。所以这条差异仍应维持此前结论：**不是当前 0.0925 / 0.215 的主嫌疑**。

综合到这里，静态优先级可以进一步收敛为：

- **P1：缺失 step-level receptor crop（最强嫌疑）**
- P2：crop 接入点与轻量 schema 的实现细节
- P3：更细的 reverse-loop / 初始化残余差异
- 低优先级：`receptor.node_t` 缺失、edge schema 命名、dynamic cross cutoff 公式本身
